## Шаг -1 — Диагностика (обязательно для любого фикса)

Перед тем как думать о решении — ответь на два вопроса:

**1. Это симптом или причина?**
- Симптом: "бот сказал неправильную фразу", "команда не отвечает", "появился дубль"
- Причина: "агент не знает границы своих знаний", "нет обработки ошибки", "ID не детерминирован"
- Если фиксируешь симптом — остановись, найди причину

**2. Это изменение кода или промпта?**
- Промпт = code-level изменение, требует того же плана/review
- Перед написанием правила в промпт: доменное ограничение ("нет доступа к файловой системе") или кейс-ограничение ("не говори про нескомпилированные заметки")?
- Кейс-ограничение → красный флаг, найди доменный принцип

## Шаг 0.5 — Стратегический выбор инструмента (обязательно перед кодом)

Перед тем как думать "как это реализовать" — спроси "а правильный ли это класс решения?"

**Чеклист:**
- Это задача классификации/routing? → есть ли у Gemini/платформы нативный примитив? (Function Calling, Tool Use, structured output, режимы SDK)
- Мы строим keyword-матчер / rule-engine / state machine? → это часто признак что надо использовать LLM-native механизм
- Есть ли в документации SDK раздел именно для этого use-case?
- Что сломается через 3 итерации если оставить текущий подход?

**Красные флаги (остановись и переосмысли):**
- Список keywords растёт с каждой итерацией → модель должна делать это нативно
- Пишем `if/elif` по типам намерений → вероятно это Function Calling
- Пытаемся "научить" prompt делать то, для чего у SDK есть явный API
- Решение работает на happy path но ломается на edge cases в production

**Формат ответа на этот шаг:**
> Класс задачи: [routing / generation / retrieval / tool dispatch / ...]
> Нативный примитив: [да — вот он / нет — объясни почему нет]
> Решение: [нативный примитив / custom — с обоснованием]

Если выбран нативный примитив — он должен быть основой плана, не надстройкой.

- Есть ли уже модуль/файл который делает то же самое что планируем добавить?

- Не создаём ли второе хранилище для данных которые уже где-то хранятся?
- Не дублируем ли вызов который уже есть выше/ниже по стеку?
- Если добавляем новый `try/except` — не перекрывает ли он уже существующую обработку?
- После изменения: есть ли код/файлы которые стали не нужны и можно удалить?

## Шаг 2 — Трассировка пути (обязательно для любого изменения затрагивающего передачу данных)

Перед написанием плана — явно проследить полный путь для каждого изменения:

```
Действие пользователя
  → какой код вызывается (файл, функция)
  → что возвращает
  → при каком условии результат передаётся дальше
  → что происходит при исключении (None? ""? молча проглочено?)
  → финальный получатель (Gemini / Telegram / файл)
```

Для каждого нового `try/except` — явно ответить: **что произойдёт если эта секция упадёт?**

Если в цепочке есть хотя бы один `except: pass` или `except: return ""` — это риск, проверить что за ним нет критичных данных.
